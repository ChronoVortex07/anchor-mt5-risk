# Remaining risks and release assumptions

1. **MQL5 compilation and demo execution are unverified.** No MetaEditor/MT5 environment or broker demo credentials were available. This is the primary release blocker. Source checks and Python fixtures cannot establish actual MT5 safety.
2. **Close is economically consequential.** The narrow EA can close all existing exposure if authorized commands are maliciously issued; a compromised SaaS/Telegram identity can realize losses. Gross reduction can increase net directional exposure. No guarantee of portfolio insurance or non-negative stop fill is made.
3. **Broker and file I/O are not one transaction.** Power loss, journal loss, request timeouts or delayed exit-deal evidence can require operator reconciliation. The system chooses lost availability over repeated closes. Operator mistakes can still clear a block incorrectly.
4. **Broker concurrency is not compare-and-swap.** Manual/other-EA changes can occur after final validation and before broker acceptance. Ticket/identifier binding and immediate rereads reduce this risk; they cannot eliminate it. Use a dedicated demo account to validate your broker and avoid other automated SL writers during execution.
5. **Agent-reported results are trusted.** The SaaS cannot independently verify broker positions. Leaked agent credentials can falsify results and heartbeat state. Installation/path/session checks are not hardware attestation against local malware or fully cloned machines.
6. **Real Telegram/TLS integrations remain unconfigured.** Bot token, webhook secret, public hostname and Login Widget domain are operator inputs. Backend tests use synthetic signed updates; browser account fixtures are mocked. No external messages or live trades were sent during development.
7. **Offsite recovery remains unactivated.** Local dump/restore mechanics were tested; a real offsite repository, encryption-key custody, scheduled job and failure alerts require operator configuration and a recovery rehearsal using actual offsite storage.
8. **Position/broker limits.** Hedging only, 128 matching positions per plan, no estimated net-cost breakeven, FOK/IOC close only. Step/minimum/residual/max-deal limits can underfill a close. BE changes whole tickets and can overshoot requested protected volume. Stops can gap and incur fees/swap/commission.
9. **Operational hardening.** Current DB role can migrate and mutate audit tables; split migration/runtime roles and external tamper-evident audit storage are future work. Define command/audit retention, user deletion and incident response before commercial operation. Backups contain sensitive account metadata.
10. **Delivery and rate behavior.** Notifications are at-least-once and may duplicate after a send/commit crash. Old messages expire after ten minutes. Source-IP budgets assume trustworthy proxy forwarding and may require tuning for large shared NATs. No always-on external alerting is configured.
11. **Deployment scale.** One backend startup migration process is expected; SQL locks support concurrent request workers, but orchestration of simultaneous migration instances is out of scope. Base images/dependencies are locked and need an ongoing patch/review process.

Recommended next milestone: compile the EA and pure MQL5 tests, configure a staging Telegram bot/HTTPS origin, then complete the demo-account checklist with recorded broker evidence. Keep `ExecutionEnabled=false` until that staged validation begins. Do not mark the system live-ready from simulator results alone.
