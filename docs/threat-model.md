# Threat model

The safety boundary is the EA's narrow command parser and executor, not HTTPS alone. The backend may request BE protection or closing existing positions; it cannot express order entry, pending orders, arbitrary SL/TP values or removal of SLs. This still grants economically consequential close authority. The local execution toggle defaults off.

| Threat | Risk | Current mitigation | Residual risk | Future mitigation |
|---|---|---|---|---|
| 1. SaaS database compromise | Account metadata/history disclosure; queued-command manipulation | Agent/session/code secrets are digests; sensitive pairing outbox encrypted using external bot secret; narrow EA protocol | Read-write attacker can alter ownership/queue and request reductions; audit DB is not tamper-proof | Separate DB roles, encrypted disks/backups, external append-only audit export |
| 2. SaaS application compromise | Attacker issues valid-looking risk commands | EA accepts only four semantic types; local buffer; validation; no entry/TP API | Attacker can close all existing positions or tighten stops at an unfavorable time | Local daily reduction limits and optional terminal-side approval |
| 3. Telegram account compromise | Attacker acts as legitimate human | Stable numeric identity, private chats, preview confirmation, ownership checks | Confirmation does not defeat an attacker controlling the account | Telegram 2FA guidance; local execution limits/second factor |
| 4. Bot token compromise | Impersonated notifications, login signature generation | Token outside DB, no token logs; distinct webhook secret; rotate both | Login auth can be forged; encrypted pairing outbox becomes readable | Independent web identity provider; faster automated rotation |
| 5. Agent token leak | Forged polls/results; visibility of current command | 256-bit random token digest; revocation; fixed account/install binding; no command-authoring authority | Attacker can falsify state/results or deny service; credential does not cryptographically prove broker acceptance | mTLS/device keys and independently signed result evidence |
| 6. MT5 machine compromise | Credential theft or modified EA/direct broker use | Files sandbox; stored API/terminal/account binding; execution toggle | Local malware can access broker terminal and bypass all EA restrictions | OS hardening, dedicated terminal user, hardware-backed keys |
| 7. Pairing-code guessing | Hijack pairing | ~60 random bits, 10-minute TTL, single use, hashed storage, shared per-IP limits | Multiple-source denial of service; user can reveal code | Global anomaly detection and abuse budgets |
| 8. Replayed command | Repeated fractional close | Fixed deadlines, unique IDs, persistent STARTED/DONE journal, recent-ID cache, session binding | Disk loss/corruption needs reconciliation; malicious backend can issue a new ID | Stronger broker-side intent ledger / local volume limits |
| 9. Duplicate polling | Parallel delivery and double execution | Account row lock, one in-flight index, same ID lease, exclusive local EA file lock, per-start session UUID | A fully compromised/cloned machine can copy/spoof identity and local state | Hardware attestation; distributed session challenge if justified |
| 10. Stale commands | Yesterday's operation executes after reconnect | 30-second absolute TTL, monotonic relative deadline, periodic sweeper, no lease extension | A broker request already sent can finish later | Measure/alert on broker response latency |
| 11. MT5 account switch | Wrong account modified | Poll login+server+installation check; latched mismatch; local check before every send | Broker state can change between final check and request; ticket-bound broker validation remains essential | Demo chaos tests around account switch and terminal events |
| 12. Wrong symbol mapping | Wrong exposure changed | Exact per-account mapping or literal broker symbol; no fuzzy matching; preview shows exact symbol/directions | Human can approve a wrong mapping or preview | Onboarding discovery with explicit approval of exact symbol |
| 13. EA copied between terminals | Two agents act with one secret | Credential path binding, exclusive local lock, per-boot session exclusion; leased executions never redelivered to a different session | Copied identical paths and actively forged session IDs are not hardware attestation | Device-bound private keys |
| 14. Backend outage | No new control/notification | MT5 remains autonomous; bounded backoff; durable queue/outbox; normal SLs remain broker-side | Remote controls unavailable; outbox may expire | Small uptime alerts and tested restore runbook |
| 15. Network partition | Broker success without server acknowledgement | Persistent exact result; idempotent resubmit; uncertain lease blocks new work | Revoked credential or corrupt journal requires human reconciliation | Assisted broker-history reconciliation, without auto-retrying close |
| 16. Malicious payload | Turn EA into general trading API | Strict bounded schemas; original bounded MQL parser rejects duplicate keys/types/unknown command fields; exact whitelist | MQL parser/compiler behavior still needs fuzzing and real compilation | Parser corpus and MT5 CI runner |
| 17. Broker rejects SL/close | Requested protection is not achieved | OrderCheck, OrderSend retcodes, post-read/deal evidence; per-ticket error codes | Market gaps, slippage, fees, freeze rules; no guarantee of zero loss | Broker-specific demo certification matrix |
| 18. Partial multi-position completion | Incorrect success claim or unsafe retry | Requested/planned/confirmed volumes separated; per-ticket retcodes; stop after uncertain response; partial status | Market/manual activity may change exposure while command runs | More detailed reconciliation UI and on-trade event correlation |

Additional close-specific risk: gross-volume reduction does not imply lower net directional exposure. Closing the losing side of a hedge can increase net risk. Previews show side totals and disclose this. No claim of guaranteed profit, stop fill or portfolio insurance is made.

Rate limiting trusts the existing reverse proxy to overwrite client forwarding headers. Backend ports are loopback-only in development and unpublished in production. Shared edge-network tenants remain within the network trust boundary. Production CORS is absent (same-origin dashboard), cookies are Secure/HttpOnly/SameSite=Strict, writes require the configured Origin, and signed Telegram login data expires after five minutes. Dashboard sessions expire after one hour.

Operational users with Docker/DB access can alter audit data and run reconciliation tooling; they are privileged administrators. The initial SQL role owns its schema for migration simplicity. Separate migration/runtime roles and tamper-evident audit storage are explicitly remaining hardening work.
